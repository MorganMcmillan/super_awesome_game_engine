# S4: PyO3 embedding cost and behavior

Date: 2026-11-09 · Status: **pass**
Code: `crates/sage_script`, benchmark `spikes/pyo3_cost` (`cargo run --release -p spike_pyo3_cost`)

## Setup
`pyo3 = "=0.30.1"`, CPython 3.12.6 (the interpreter found at build time), numpy 2.0.2, Windows 11, release build. The workload integrates `pos += vel * dt` for N entities with f32 columns stored in Rust.

## Results (per tick; a 60 Hz tick has 16.7 ms)

| N | A: one Python call per entity | B: one call, Python loop over memoryviews | C: one call, numpy views (zero copy) |
|---|---|---|---|
| 1 000 | 0.34 ms | 0.61 ms | 0.017 ms |
| 10 000 | 3.97 ms | 7.22 ms | 0.031 ms |

- Attaching to the interpreter (taking and releasing the GIL): about 190 ns.
- A costs about 0.4 µs per entity, which is a quarter of the tick budget at 10k entities. B is slower than A: indexing memoryviews in Python costs more than crossing FFI with floats. C is about 130 times faster than A at 10k entities and almost flat in N.
- These numbers support the [Leaning] ramp in 3.4: per-entity Python for beginners at small N, column views (numpy over Flecs columns) for hot loops, native systems after that.

## Behavior
- **Hash seed:** the interpreter is started through `PyConfig` with `use_hash_seed = 1, hash_seed = 0`, the in-process equivalent of `PYTHONHASHSEED=0`. Setting the environment variable from inside the process is not reliable on Windows, because the C runtime caches the environment. Asserted by `sage_script` tests.
- **Isolated config:** `PYTHONPATH`, other environment variables and the user site directory are ignored, so machine setup cannot change simulation behavior. The global site-packages stays visible, which is how numpy was found.
- **Script isolation:** each script runs in a fresh globals dict. Two simulations in one process never share script state, which the replay harness depends on.
- **GIL:** one interpreter per process, initialized once. After init the GIL is released, so any thread can call `Python::attach`. Calls from parallel test threads serialize on the GIL. Free-threaded Python was not evaluated.
- **Linking:** dynamic linking to `python312.dll`. The DLL must be on `PATH` at run time (true for a standard install). Shipping a game will need a bundled interpreter (10.5).
