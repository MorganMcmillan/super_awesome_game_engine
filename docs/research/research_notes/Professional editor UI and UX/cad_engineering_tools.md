# CAD and technical/procedural software UI/UX: lessons for a game engine editor

Research date: 2026-11-14. Versions are noted where a source gave them. Sources are a mix of vendor documentation (Autodesk, Dassault, Onshape/PTC, SideFX), Autodesk Research HCI papers, peer-reviewed HCI work, and practitioner material, which is marked *anecdotal*. Several findings come from search-result summaries of pages that were not fetched in full. Those are flagged "(summary)" so the report writer can weigh them.

## AutoCAD: the command line, aliases, dynamic input, precise input, snaps, the ribbon, scripting

### Takeaway
AutoCAD's command line survived because it is a *forgiving, searchable, typed* way in that sits beside the GUI. It has AutoComplete, mid-string search, AutoCorrect and synonyms (since 2014), it is echoed at the cursor (dynamic input), and it leads straight into scripting (AutoLISP since 1986, available in LT since 2024). The 2009 ribbon caused a backlash among experts, but Autodesk kept an escape hatch (the Classic workspace), and many users came back to the ribbon after a while. Precision comes from snaps, tracking and typed coordinates, not from steady hands.

### Cited Findings
- **AutoCorrect, mid-string search and synonyms (AutoCAD 2014).** A mistyped command ("TABEL") is corrected to the closest valid one (TABLE) instead of returning "unknown command". AutoComplete gained mid-string search, so typing a word lists every command that contains it. A built-in synonym list maps intent words to commands: SYMBOL gives INSERT, ROUND gives FILLET. All of these are on by default and set in "Input Search Options". — [AutoCAD 2014 Preview Guide (JTB World mirror)](https://jtbworld.com/download/autocad2014previewguide.pdf) (summary); [CAD Notes: AutoCAD 2014 command line](https://www.cad-notes.com/autocad-2014-command-line/) (summary)
- Before 2014, AutoComplete matched prefixes only: typing ROTATE showed only ROTATE and ROTATE3D. — [CAD Notes](https://www.cad-notes.com/2013/04/autocad-2014-command-line/) (summary)
- Users can add their own AutoCorrect and synonym entries through Edit Aliases on the Manage tab. — [LT 2014 blog: "LT2014's command line, it's here to stay"](https://ltisacad.blogspot.com/2013/03/lt2014s-command-line-its-here-to-stay.html) (summary, *practitioner*)
- Most of the 2014 command-line features also work in dynamic input, the prompt shown at the cursor. One source says internet search works only in the command line, so the sources disagree on how far the features extend. — [Preview Guide (Scribd copy)](https://www.scribd.com/document/432767895/autocad2014previewguide-pdf); [CAD Notes](https://www.cad-notes.com/autocad-2014-command-line/) (summary)
- Autodesk's help has a dedicated "command line suggestion list" topic, documented in LT from 2015 on. — [Autodesk Help: To Work With the Command Line Suggestion List (LT 2016)](https://help.autodesk.com/cloudhelp/2016/ENU/AutoCAD-LT/files/GUID-74478DCE-92D4-49B1-93E9-DCF09D57FA0D.htm)
- **Object snap tracking** builds temporary alignment paths from "acquired" snap points, by default at 0/90/180/270 degrees, or at polar angles if configured. F11 toggles it. **Polar tracking** shows alignment paths at a set angle increment (default 90 degrees, POLARANG), toggled with F10. Polar tracking and Ortho exclude each other. — [Autodesk Help: About Tracking Points Automatically Using Object Snaps (2026 LT)](https://help.autodesk.com/cloudhelp/2026/ENU/AutoCAD-LT/files/GUID-665DC37F-8C3E-414A-9369-72A13C0BE07A.htm); [About Polar Tracking and PolarSnap (2027 LT)](https://help.autodesk.com/cloudhelp/2027/ENU/AutoCAD-LT/files/GUID-7EC3C63D-EA4E-4E65-A676-C3A3627E3F19.htm); [Object Snap Tracking (Did You Know, 2022)](https://help.autodesk.com/cloudhelp/2022/ENU/AutoCAD-DidYouKnow/files/GUID-6FB309A8-2696-4383-8277-950E9E2756A8.htm)
- **Snap cycling.** When several object snaps are available at one point, Tab cycles through them. Shift plus right-click opens the one-shot object snap override menu. — [Autodesk Help: To Specify a Precise Point Location (LT 2026)](https://help.autodesk.com/cloudhelp/2026/ENU/AutoCAD-LT/files/GUID-392167BC-8032-44D9-B4A9-DF4AC00DF5C4.htm) (summary)
- **The 2009 ribbon reaction** (*anecdotal*, self-selected blog and forum comments from 2008–2010). Critics said the ribbon was slower, took more clicks and used more screen space. A 25-year user wrote that it was "the first time I found I could not use autocad with the default interface". Defenders said the old interface had become fragmented and inconsistent. Many users switched back to Classic and later returned to the ribbon, or kept it auto-hidden. — [cad nauseam: "AutoCAD 2009 – Why do you hate the Ribbon?" (2008-06-16)](https://www.cadnauseam.com/2008/06/16/autocad-2009-why-do-you-hate-the-ribbon/); [cad nauseam: "How do you use the Ribbon?" (2008-05-28)](https://www.cadnauseam.com/2008/05/28/autocad-2009-how-do-you-use-the-ribbon/); [CADTutor: Productivity articles, July 2008](https://www.cadtutor.co.uk/corner/2008/july.php); [The CAD Geek: Introduction to the AutoCAD 2009 Ribbon](https://thecadgeek.com/blog/introduction-to-the-autocad-2009-ribbon/)
- **The escape hatch.** Autodesk kept an "AutoCAD Classic" workspace after the ribbon arrived. Practitioners published "putting things back to normal" guides for 2009, 2010 and 2011, which shows that reverting was common enough to need a recipe. — [cad nauseam: AutoCAD 2009 – Putting things back to "normal"](https://www.cadnauseam.com/2008/03/27/autocad-2009-putting-things-back-to-normal/); [2010 edition](https://www.cadnauseam.com/2009/06/16/autocad-2010-putting-things-back-to-normal/); [Graitec: How to restore AutoCAD Classic workspace](https://graitec.com/us/tech-resources/how-to-restore-autocad-classic-workspace/)
- **Scripting as the ceiling.** AutoLISP dates to AutoCAD 2.18 (1986). AutoCAD LT 2024 was the first LT release to include it, with its own startup file name (ACADLTDOC.lsp) and no 3D calls. Autodesk's stated reason was to let organizations running both products share their automation. — [Autodesk blog: How to Use AutoCAD LT and AutoLISP](https://www.autodesk.com/blogs/autocad/autocad-lt-2024-autolisp/); [Autodesk Help: AutoLISP (AutoCAD LT 2024 What's New)](https://help.autodesk.com/cloudhelp/2024/ENU/AutoCAD-LT-WhatsNew/files/GUID-5FB57480-C9BE-4E3D-BEDF-D86035928FFA.htm); [AUGIWorld: AutoCAD LT gets the power of AutoLISP](https://augi.com/articles/detail/autocad-lt-gets-the-power-of-autolisp)
- **Why the typed path matters (HCI evidence).** Lane, Napier, Peres and Sándor (IJHCI 18(2), 2005) found that most users keep issuing commands through menus and toolbars even though a keyboard shortcut typically takes about half the time. Users do not make the move to the faster method on their own. — [dblp record](https://dblp.uni-trier.de/rec/journals/ijhci/LaneNPS05.html); finding as reported in [SciTePress 2019 paper citing it](https://www.scitepress.org/Papers/2019/84945/84945.pdf) and [Bohrium: "Satisficing and the use of keyboard shortcuts"](https://www.bohrium.com/paper-details/satisficing-and-the-use-of-keyboard-shortcuts-being-good-enough-is-enough/813247484091432961-2808) (secondary)
- **CAD users plateau.** Bhavnani and John ("The strategic use of complex computer systems", *HCI* 15(2-3), 2000, pp. 107–137, CMU HCII) report that "despite experience, many users with basic command knowledge do not progress to an efficient use of complex computer applications". They argue that strategy knowledge (for example, use arrays and copies rather than drawing every element by hand) should be taught and designed for explicitly. Related CMU work found experienced CAD users drawing in ways that copy manual drafting. — [Bibliographic record](https://acnpsearch.tweb-dev.unibo.it/singlejournalindex/79480775); [Exploring the unrealized potential of computer aided drafting](https://www.academia.edu/55693470/Exploring_the_unrealized_potential_of_computer_aided_drafting); [CMU: Human-Computer Interaction in CAD project page](https://www.andrew.cmu.edu/user/ujf/HCI_CAD.html)
- **Novice use as rehearsal for expert use (Autodesk Research).** Marking menus rest on "self-revelation, guidance and rehearsal": novices select from a visible menu with the same gesture an expert makes blind. In a field study (CHI 1994), a mark was on average about 3.5 times faster than selecting from the menu, and experts still went back to the visible menu to refresh their memory. Maya's Hotbox was designed so that "novice operation was a rehearsal of expert behavior". — [Kurtenbach thesis, The Design and Evaluation of Marking Menus](https://research.autodesk.com/app/uploads/2023/03/the-design-and-evaluation.pdf_recCzWoTgz02K2Ubb.pdf); [User learning and performance with marking menus (CHI '94)](https://www.research.autodesk.com/publications/user-learning-and-performance-with-marking-menus/); [The Hotbox: efficient access to a large number of menu items](https://research.autodesk.com/app/uploads/2023/03/the-hotbox-efficient-access.pdf_recBEaTweOOJdwYy2.pdf); [The limits of expert performance using hierarchic marking menus](https://research.autodesk.com/app/uploads/2023/03/the-limits-of-expert.pdf_recyw5wL6ekPqcE4Q.pdf)

### Inferences
- The command line works because three things are true at once. It is *one flat namespace* of every operation, it is *forgiving* (fuzzy, synonyms, autocorrect), and it is *the same thing the scripting layer calls*. Recording a session gives you a script, so the typed path feeds directly into automation.
- Dynamic input shows the novice-to-expert bridge in miniature. The prompt and the typed values sit where the eyes already are, so typing a length while drawing is not a mode switch.
- The ribbon episode suggests that reorganizing a GUI for discoverability is fine *if* the expert path (typed commands, aliases, old layout) is kept and can be reached in one action. The 2009 anger was aimed at losing a fluent workflow, not at the ribbon as such.
- Lane et al. and Bhavnani and John together say that experts are not produced automatically. The UI must actively show the faster path, for example by showing the shortcut or the typed equivalent every time a menu is used. Marking menus are the strongest evidence that the novice path can *be* practice for the expert path.

### Gaps
- No full text of the Autodesk 2009 ribbon design rationale, and no formal satisfaction survey for 2009 was found. All reaction evidence is self-selected and anecdotal.
- The history of aliases (`acad.pgp`) and the introduction date of dynamic input (believed to be AutoCAD 2006) were not verified from primary sources in this pass.
- No quantitative study comparing AutoCAD's command line with ribbon use specifically was found. Lane et al. is about shortcuts in general (Office-type tasks).
- The Properties palette and selection cycling (the SELECTIONCYCLING variable) were not fetched from primary docs. Only snap cycling (Tab) was confirmed.

## Parametric history: Fusion timeline, SolidWorks FeatureManager, Onshape feature list, versioning and branching, and editable history versus undo

### Takeaway
Parametric CAD stores the *recipe*, an ordered list of features with parameters, not the result. The result is regenerated from the recipe. The user can therefore roll back, edit an early step, reorder, or suppress, and everything downstream recomputes. Onshape went furthest: the definition is a chain of immutable microversions (the equivalent of commits), workspaces are branches, merges replay changes, and undo is per user, implemented as a *new* inverse change rather than a rewind. The price is reference fragility. A later feature that points at a face or edge produced by an earlier one can break when that face's identity changes. This is the "topological naming problem", mitigated by heuristics in commercial kernels and only partly fixed in FreeCAD 1.0.

### Cited Findings
- **Onshape's three data layers.** UI state (selection, camera, tab), the Part Studio *definition* (feature list, names, colors, imports), and *regeneration results* (b-rep, display triangles, errors). Only the definition is stored. The results "are cached, but they can always be rebuilt from the definition." — [Ilya Baran, "Under the Hood: How Collaboration Works", Onshape blog, 2015-06-22](https://www.onshape.com/en/blog/under-the-hood-how-collaboration-works)
- **Microversions.** Each state of the definition is "an eternal, immutable object that we internally call a microversion", and each stores "only the changes relative to its parent". Changes address features by internal ID, so renames do not break them. Changes are meant to apply to their parent but can be applied to a different microversion. — [Baran 2015](https://www.onshape.com/en/blog/under-the-hood-how-collaboration-works)
- **Multi-user editing.** Collaboration was a requirement from day one: the system supported simultaneous editing of a part before it had sweeps or assemblies. Independent change records from several users are applied to the latest microversion. — [Baran 2015](https://www.onshape.com/en/blog/under-the-hood-how-collaboration-works)
- **Undo is not rewind.** Undo is per user and "cannot simply take the Part Studio back to an earlier microversion". It creates a new microversion that applies the inverse of your change on top of the latest one. Restoring history is a separate operation and can remove collaborators' edits. — [Baran 2015](https://www.onshape.com/en/blog/under-the-hood-how-collaboration-works)
- **Branching and merging.** Workspaces are branches, microversions form a tree, and a merge creates a new microversion holding the "from" changes that are not yet in "to". In a dimension conflict the "from" side wins, and the author says merge conflicts in the git sense should not happen. Follow Mode and Compare are built on the same immutable history, which also lets engineers trace how a document reached a broken state. — [Baran 2015](https://www.onshape.com/en/blog/under-the-hood-how-collaboration-works)
- **User-facing model.** Versions are named, immutable snapshots. Workspaces are the in-progress state of a branch. The history panel can restore the document to any point. Merges carry actions from one branch to another. — [Onshape Help: Versioning and Branching](https://cad.onshape.com/help/Content/Document/versions_and_history.htm); [Onshape Help: Document Management](https://cad.onshape.com/help/Content/Document/document_management.htm?TocPath=Document+Management%7C_____0); [Onshape Learning: Data Management](https://learn.onshape.com/learn/course/onshape-hands-on-test-drive/collaboration-and-data-management/data-management); a forum answer compares versions to git tags: [Onshape forum: "workspace" and "main"](https://forum.onshape.com/discussion/5752/in-onshape-speak-what-is-the-definition-of-workspace-and-what-is-main-all-about); releases and approval workflows sit on top: [Onshape blog: Workflows, Revisions, and Release Management](https://www.onshape.com/en/blog/revisions-releases-custom-workflows-product-data-organization-cloud-native-cad)
- **Entities exist per microversion.** The API docs say Part Studio entities "can appear, disappear, and reappear depending on the current microversion", and that a topology ID from one microversion can be translated into a *set* of IDs in the current one. — [Onshape API docs: Architecture](https://onshape-public.github.io/docs/api-intro/architecture/)
- **How Onshape addresses topology** (forum answers from Onshape staff, summary). FeatureScript separates *transient* queries, which are invalid after a change, from *robust* queries (select by identity, built with `makeRobustQuery`) and *tracking* queries (new entities derived from existing ones, `startTrackingIdentity`). Each operation records the dependencies of the topology it creates. Identity follows a single lineage: if a face is split, its identity disappears. `setExternalDisambiguation` lets a feature author choose which identity disambiguates an operation. — [Onshape forum thread (Baran answer)](https://forum.onshape.com/discussion/comment/75864); [Onshape forum: broken references after renames](https://forum.onshape.com/discussion/17478/how-to-handle-broken-references-when-modifications-to-a-part-studio-cause-named-parts-to-be-renamed); [Onshape Tech Tip: Query Explorer in FeatureScript](https://www.onshape.com/en/resource-center/tech-tips/tech-tip-how-to-use-query-explorer-in-featurescript)
- **The topological naming problem (TNP).** After an operation such as a pad, fillet or chamfer, a sub-shape can get a new internal name, and dependent features then "break or be incorrectly computed". FreeCAD's wiki says most CAD software "has heuristics to reduce the impact". It recommends referencing datum planes and local coordinate systems rather than generated faces. — [FreeCAD wiki: Topological naming problem](https://wiki.freecadweb.org/Topological_naming_problem); [GitHub mirror](https://github.com/FreeCAD/FreeCAD-documentation/blob/main/wiki/Topological_naming_problem.md)
- **FreeCAD 1.0 (Nov 2024) merged RealThunder's naming algorithm.** The wiki says it is "not intended to fix every failure". Ondsel's blog headline says TNP is "(officially) history". Sources therefore disagree on solved versus mitigated. — [Ondsel blog: FreeCAD's topological naming problem is (officially) history](https://www.ondsel.com/blog/toponaming-problem-is-history/); [FreeCAD wiki](https://wiki.freecadweb.org/Topological_naming_problem)
- *Anecdotal:* Hacker News commenters say they "never had an issue in OnShape but got hit with it every time in FreeCAD", and that SolidWorks and Onshape do not hide the problem but have better algorithms that still "break down in much more complex models". — [Hacker News: Topological Naming Problem](https://news.ycombinator.com/item?id=47097446)
- **Fusion timeline behavior.** When you drag a feature, Fusion highlights its dependencies: preceding features it depends on when dragging backward, and features that depend on it when dragging forward. Inactive features can be hidden ("Hide All Inactive Features"). Users report friction: the history marker cannot be rolled to a collapsed group, and some drags fail silently or "teleport" features (*anecdotal*). An Autodesk employee explained that component moves not "captured" into the timeline are lost when the marker moves. — [Autodesk forum: Timeline feature requests](https://forums.autodesk.com/t5/fusion-support-forum/timeline-feature-requests/m-p/14293656); [Autodesk forum: component history marker position](https://forums.autodesk.com/t5/fusion-support/component-history-marker-position-is-permanently-saved-and-can-t/m-p/8970654); [Autodesk forum: shortcut for "roll history marker here"](https://forums.autodesk.com:443/t5/fusion-360-ideastation-archived/shortcut-for-quot-roll-history-marker-here-quot/idi-p/7576685); [VDCI: Organize your Fusion timeline with groups](https://vdci.edu/learn/cad/organize-your-fusion-360-timeline-with-groups-editing-and-grouping-objects)
- **Parametric plus direct editing.** Autodesk's own guidance on timeline edits is that Fusion supports both parametric and direct edits, and you should "use the best tool for the situation". Fusion also lets you turn off history capture for direct modeling. — [Autodesk Fusion blog: Timeline edits in Fusion](https://www.autodesk.com/products/fusion-360/blog/timeline-edits-in-fusion/)

### Inferences
- **History versus undo.** An undo stack is a *linear log of edits to state*, so going back loses everything after that point. Parametric history is an *ordered program* whose steps can be edited in place, with downstream steps re-executed. Onshape keeps both: the feature list is the program, and the microversion graph is the edit log of that program. Its undo is an inverse edit appended to the log, not a truncation. That design survives collaboration and keeps history immutable.
- The dependency highlighting shown while dragging a feature is a cheap, high-value pattern. It makes the hidden dependency graph visible exactly when the user is about to violate it.
- **TNP generalizes** to any system where a later step refers to something an earlier step *generated*, by position or index rather than by stable identity. The CAD fixes are the familiar ones. Reference stable datums (in ECS terms, StableIds and authored entities, not generated ones). Record lineage when a step creates things, so a reference can be re-resolved. When re-resolution is ambiguous, fail loudly and show the broken reference rather than silently picking the wrong one.
- Separating the *definition* (stored) from *results* (cached and rebuildable) from *UI state* (not part of the document) is the same split as authored scene versus live world versus editor view state.

### Gaps
- Primary SolidWorks documentation for the FeatureManager design tree (rollback bar, suppress, reorder, "What's Wrong" dialog) was not fetched. Its behavior is assumed similar but not verified here.
- No HCI study was found that measures how comprehensible parametric history is to novices, or how often it breaks. Evidence for reference fragility is documentary and anecdotal.
- Primary Fusion help pages for suppress and the capture-history toggle were not fetched.

## Constraints and dimensions as declarative editing

### Takeaway
Sketch constraints let users state *relations* (parallel, tangent, length = 40, equal) and leave the solver to find positions. The UI's key job is to show the *remaining degrees of freedom*. In SolidWorks blue means under-defined (free to move), black means fully defined, and red means over-defined or unsolvable. A solver assistant (SketchXpert) helps resolve conflicts.

### Cited Findings
- SolidWorks sketch states: blue means "the entity is not fixed" (Under Defined, shown in the status bar), black means fully defined, and red marks over-defined geometry (for example from redundant dimensions) or unsolvable items. SketchXpert is the tool for resolving conflicts. — [SOLIDWORKS Help 2019: Sketch States](https://help.solidworks.com/2019/english/SolidWorks/acadhelp/c_sketch_states_acadhelp.htm); [SOLIDWORKS Help 2015: Sketch Geometry Status](https://help.solidworks.com/2015/ENGLISH/SolidWorks/sldworks/c_Sketch_Geometry_Status.htm); [SOLIDWORKS Help 2012: Sketch States](https://help.solidworks.com/2012/English/SolidWorks/acadhelp/Sketch_States.htm)
- Third-party sources give more color states (yellow = invalid, pink = unsolvable), which conflicts with the help's red for unsolvable. A 2010 legacy page lists green = selected. The color set appears to have changed across versions. — [CADimensions blog](https://www.cadimensions.com/?p=3383); [SOLIDWORKS 2010 Sketch Options (legacy)](https://help.solidworks.com/2010/english/solidworks/sldworks/legacyhelp/sldworks/sw_sketch/HIDD_OPTIONS_SKETCH.htm)
- Practitioner tutorials stress fully defining sketches so that downstream edits behave predictably, and recommend Display/Delete Relations for finding conflicting constraints. — [leyaa.ai: why fully defined sketches matter](https://leyaa.ai/core-engineering/learn/solidworks/part-1/solidworks-why-fully-defined-sketches-matter) (secondary study site); [Cadasio: Getting started with sketching in SOLIDWORKS, part 4](https://cadasio.com/post/getting-started-with-sketching-in-solidworks-a-beginners-guide-part-4)

### Inferences
- The DOF color code is a *status of a declarative system shown on every element*. It answers "what is still free?" at a glance, which raw constraint lists cannot. A game analog: color or badge entities and components by whether their values are authored, derived by a rule, or overridden, and flag over-constrained rule sets (two systems writing the same component every tick).
- Declarative game rules (ECS systems as queries: "every entity with Health <= 0 gets Dead") behave like constraints in that the user states the invariant, not the procedure. The CAD lesson is that the editor must show *which rule determined this value* and *where rules conflict*, the equivalent of red/SketchXpert. Otherwise declarative editing feels like magic when it breaks.
- Constraints serve both ends of the skill range. Novices get "snap-and-stick" behavior (inferred constraints while drawing). Experts get exact, typed dimensions that can be driven by named parameters.

### Gaps
- Primary docs for constraint inference while sketching (automatic relations) and for named-parameter or equation tables (Fusion "Change Parameters", SolidWorks Equations) were not fetched.
- No empirical study of the DOF color display's effect on novice success was found.

## Houdini: procedural node networks, parameters with expressions, HDAs, and the learning curve

### Takeaway
Houdini makes the network itself the document. Every operation is a node with parameters. Parameters can hold expressions (HScript or Python) and channel references to other parameters. Any network can be wrapped into a digital asset (HDA): a new node type with a curated, promoted interface, versioning, and an expandable file format for source control. This is how a TD's work becomes an artist's tool. The learning curve is widely described as being about a "procedural mindset" more than about the interface (anecdotal).

### Cited Findings
- Channel references let custom spare parameters and digital-asset interfaces "control other nodes". They can be created with Copy/Paste Reference from a parameter's context menu. Parameters accept HScript expressions by default, or Python, with globals such as `$F` (current frame). — [SideFX Houdini docs: Networks and parameters (expressions)](https://www.sidefx.com/docs/houdini/network/expressions.html); [SideFX: `ch` expression function](https://www.sidefx.com/docs/houdini/expressions/ch.html); [SideFX: expression functions index (Houdini 22.0)](https://www.sidefx.com/docs/houdini/expressions/index.html)
- Promoting a parameter copies it onto the asset's interface and replaces the inner node's value with a reference back to the asset's copy. Spare parameters can be added to individual node instances, not only to assets. — [SideFX docs: Digital assets UI (Houdini 20.0)](https://www.sidefx.com/docs/houdini/assets/asset_ui.html) (summary); [SideFX docs: Networks and parameters](https://www.sidefx.com/docs/houdini/network/expressions.html)
- Digital assets "create reusable nodes and tools from existing networks". Houdini has "two different systems for versioning assets" (versions and namespaces). Asset files can be expanded into plain files for diffing and source control. — [SideFX docs: Digital assets (Houdini 22.0 index)](https://www.sidefx.com/docs/houdini/assets/index.html)
- Node networks and help reference: [SideFX docs: Network editor (Houdini 22.0)](https://www.sidefx.com/docs/houdini/network/index.html); [SideFX: Operator type properties window](https://www.sidefx.com/docs/houdini/ref/windows/optype.html)
- **Houdini Engine** exposes HDAs inside Unity and Unreal, where the asset's promoted parameters become the host editor's inspector. This is the "TD builds, game artist uses" pipeline. — [Houdini Engine for Unity: Parameters](https://download.sidefx.com/docs/unity18.0/_parameters.html); [SideFX: Houdini Engine for Unreal, parameters](https://www.sidefx.com/docs/houdini/unreal/parameters.html)
- *Anecdotal* learning curve: one Medium guide estimates the interface takes a weekend, basic procedural work a few weeks, and the "procedural mindset" a few months. It warns that shelf tools silently build multi-level networks, so beginners should add nodes one at a time from the Tab menu to see what is happening. — [Medium: Houdini for the First Time](https://medium.com/@sarah.hyperdense/houdini-for-the-first-time-interface-nodes-and-the-procedural-mindset-6721c1cc5613). Several SEO-style blogs give inconsistent timelines and list building a first HDA as an early milestone. — [Artivoxa: How Long Does It Take to Learn Houdini?](https://www.artivoxa.com/how-long-does-it-take-to-learn-houdini-a-realistic-timeline/); [Artivoxa: Is Houdini worth learning in 2026?](https://www.artivoxa.com/is-houdini-worth-learning-in-2026-an-honest-answer/) (low reliability)

### Inferences
- An HDA is a *capability boundary*. Experts build networks, then expose a small, named, ranged interface, and the result appears to novices as an ordinary node. For a game engine, a Python-defined system or prefab with a declared parameter interface (inspector-visible, typed, ranged) would be the HDA analog. The block editor's palette could list these as blocks.
- "Shelf tools that build hidden networks" is a warning about one-click helpers. A beginner convenience that generates structure should leave the generated structure readable and inspectable (in this engine: readable Python and visible entities), or it teaches nothing and cannot be debugged.
- Expressions in any parameter (`$F`, `ch("../x")`) form a *gradual* ceiling: a constant becomes a formula, then a reference, then code, without leaving the inspector.

### Gaps
- No SideFX design writing on the learning curve, and no usage statistics, were found. Learning-curve evidence is anecdotal or SEO content.
- HDA locking and "editable nodes" semantics were not fetched in detail.
- The phrase "everything is a node" was not found verbatim in SideFX docs. Treat it as community shorthand.

## Precision and spatial editing: snapping, gizmos, grid, units, measuring, viewport navigation

### Takeaway
Engineering tools get precision from *inference plus typed values*: snaps to geometric features, temporary alignment tracking, polar increments, and the option to type exact numbers at any prompt. Viewport navigation is not standardized. Fusion ships presets copying SolidWorks, Inventor, Alias, Tinkercad and PowerMill, which openly admits that muscle memory from other tools is a switching cost.

### Inferences
- In a 2D-first engine with a pixel-perfect camera, the CAD equivalents are: snap to pixel or grid by default, snap to other entities' edges, centers and anchors, temporary alignment guides from hovered entities (object snap tracking), and *typed values during a drag* (dynamic input: type "32" while dragging to move exactly 32 px). Tab to cycle overlapping snap or selection candidates is directly transferable.
- Navigation presets ("Unity", "Godot", "Blender", "Aseprite" style) are cheap to offer, because the input map is already data (`InputMap` in `sage_platform`). They remove a real switching cost for intermediate users who come from other engines.
- Units matter less in a pixel game, but the CAD principle "every number has a unit and a display precision" applies to ticks versus seconds and pixels versus world units, both of which the deterministic core already separates (`TICK_DT`).

## Serving beginners and experts in one product

### Takeaway
Vendors split the floor and the ceiling in two ways. One is *product tiers* (AutoCAD LT versus full; Fusion for Personal Use with caps). The other, stronger approach is *one product with progressive paths*: GUI and command line over the same commands, marking menus whose novice use rehearses the expert gesture, parameters that accept constants or expressions, and HDAs that hide expert networks behind a simple interface. Tier splits erode over time: LT gained AutoLISP in 2024.

### Cited Findings
- AutoCAD LT lacked AutoLISP until 2024. Its addition was justified by sharing automation across mixed LT and full installations. — [Autodesk blog: AutoCAD LT and AutoLISP](https://www.autodesk.com/blogs/autocad/autocad-lt-2024-autolisp/)
- Fusion for Personal Use is free for non-commercial, home-based use under about USD 1,000/year revenue. It is renewable every three years and limited in CAM, electronics, documentation, collaboration, file types and support. Secondary sources also cite a 10-editable-document limit and restrictions on simulation and generative features, but they disagree on details, and current Autodesk terms were not fetched. — [Autodesk Fusion blog: Fusion for Personal Use vs. Autodesk Fusion](https://www.autodesk.com/products/fusion-360/blog/fusion-for-personal-use-vs-autodesk-fusion/); [Fabbaloo: Autodesk changes Fusion 360 free license terms](https://www.fabbaloo.com/?p=37763); [Stack Sheriff: Fusion personal-use license read line by line](https://stacksheriff.com/3d-printing/fusion-360-free-personal-license/?format=md) (secondary)
- Marking menus and the Hotbox as explicit novice-to-expert designs (Autodesk Research): see the AutoCAD section. — [Autodesk Research: marking menus](https://www.research.autodesk.com/publications/user-learning-and-performance-with-marking-menus/)
- Users with experience still plateau at basic command knowledge (Bhavnani and John 2000) and do not switch to faster methods on their own (Lane et al. 2005): see the AutoCAD section.
- Fusion's own guidance is to mix parametric (history) and direct editing "using the best tool for the situation". Direct editing is the lower-floor mode. — [Autodesk blog: Timeline edits in Fusion](https://www.autodesk.com/products/fusion-360/blog/timeline-edits-in-fusion/)

### Inferences
- Tiering by product is a business decision, not a UX one. The UX lesson is "one engine, layered disclosure", where every beginner action is visibly the same operation an expert would type or script.
- Plateaus are the default outcome. Designing *for* the intermediate (teaching strategies such as "make a prefab and instance it, don't copy and paste 20 times") matters as much as the floor and the ceiling.

### Gaps
- No vendor data was found on how many users ever move from GUI to command line or scripting.

## Implications for a game engine editor at each skill level (beginner, intermediate, expert), including parametric history versus the deterministic input log

### Takeaway
Treat the editor like Onshape treats a Part Studio. The *definition* is authored scene data plus Python source. *Results* are the live world, regenerated or replayed deterministically. *UI state* is editor-only. Give one command namespace that serves the GUI, a searchable command bar and Python. Make dependencies and declarative-rule status visible. Make every beginner action a rehearsal of the expert path. Parametric history and the deterministic input log are the same idea at two layers: a recipe that regenerates state.

### Cited Findings
- The patterns below draw on the findings cited above: Onshape's definition/results/UI-state split, microversions and inverse-change undo ([Baran 2015](https://www.onshape.com/en/blog/under-the-hood-how-collaboration-works)); AutoCAD's forgiving command line ([2014 Preview Guide](https://jtbworld.com/download/autocad2014previewguide.pdf)); the plateau and shortcut evidence ([Lane et al. 2005](https://dblp.uni-trier.de/rec/journals/ijhci/LaneNPS05.html); [Bhavnani and John 2000](https://acnpsearch.tweb-dev.unibo.it/singlejournalindex/79480775)); rehearsal ([Kurtenbach](https://research.autodesk.com/app/uploads/2023/03/the-design-and-evaluation.pdf_recCzWoTgz02K2Ubb.pdf)); TNP ([FreeCAD wiki](https://wiki.freecadweb.org/Topological_naming_problem)); HDAs ([SideFX](https://www.sidefx.com/docs/houdini/assets/index.html)); DOF colors ([SOLIDWORKS Help](https://help.solidworks.com/2019/english/SolidWorks/acadhelp/c_sketch_states_acadhelp.htm)); navigation presets ([Fusion preferences](https://help.autodesk.com/cloudhelp/ENU/Fusion-GetStarted/files/GUID-878489CD-3A23-4303-8450-C2F4F8E410B1.htm)).

### Inferences

**Beginner (low floor)**
- Direct manipulation first, with snapping on by default (grid or pixel, and snap to other entities' edges and centers), alignment guides from hovered entities, and visible snap markers. Typing a number during a drag gives exact placement without opening a dialog (dynamic input).
- A forgiving command bar (Ctrl+Space style). Fuzzy and mid-string matches, synonyms ("enemy" finds "spawn prefab", "round" finds "fillet"-style aliases), autocorrect, and every result shows its shortcut and the equivalent Python (`world.spawn(...)`) so the beginner sees the expert path. This answers the Lane et al. finding that users don't migrate on their own.
- Status colors for declarative state, borrowed from SolidWorks DOF colors. Show whether a component value is authored, inherited from a prefab, or written by a system each tick (and which system). Flag conflicts (two systems writing the same field) in red, with a "resolve" helper.
- Undo always works and is never a puzzle. Following Onshape, undo appends an inverse scene diff (`sage_editor::history` already stores undo as scene differences) and never truncates shared history.
- Helpers and wizards must leave readable output: plain Python and visible entities in the block editor and outliner. This avoids Houdini's shelf-tool trap of generating structure nobody can read.

**Intermediate (where people plateau)**
- Prefabs with promoted parameters act as HDAs. An author marks which fields of a prefab or kit system are its public interface (with ranges and units). Instances show only those, and the block palette lists them as blocks. Editing the prefab updates instances. The engine already has inheritable style prefabs.
- Expressions in inspector fields: a constant can become an expression (`= other.x + 16`, `= tick * 2`) and then a script, in place, like Houdini parameters. Expressions must be evaluated deterministically inside the simulation and hashed.
- Teach strategies, not just commands (Bhavnani and John): suggest "make this a prefab" when the user copy-pastes the same entity several times, and "use a query or system" when they hand-edit many entities identically.
- Navigation presets (Godot-, Unity-, Blender-like) through the existing `InputMap`, plus rebinding.
- Dependency highlighting during reorder, borrowed from Fusion. When reordering systems or pipeline phases, or reparenting UI and `ChildOf` nodes, highlight what this item depends on and what depends on it.

**Expert (high ceiling)**
- One command namespace. Every GUI action is a named command with typed arguments, callable from the command bar, from Python, and recordable to a script, as AutoCAD commands map to AutoLISP and scripts. Macros come free when the editor's own actions are logged as commands.
- Branching and versioning of the authored scene like Onshape: immutable versions (snapshots of `sage-scene v1` plus source), workspaces or branches, and merges as replays of changes keyed by StableId (never by Flecs entity id). A "from wins" rule for field-level conflicts is defensible for scene data, as Onshape's experience suggests.
- Scripted tools packaged as assets: Python editor extensions with a declared parameter interface, versioned like HDAs, sandboxed per CLAUDE.md's untrusted-code rule.

**Parametric history versus the deterministic input log and replays**
- *Same idea, two layers.* Parametric CAD stores an ordered recipe (features with parameters) and regenerates geometry. A deterministic simulation stores initial state, the input log and the code, and regenerates every tick's world. In both, the stored thing is small and authoritative, the result is a cache, and editing an early step re-executes everything after it. "Edit rule, replay recording, compare per-tick hashes" is the game counterpart of "edit early feature, regenerate, check for errors".
- *Rollback marker equals tick scrubbing.* Fusion's history marker maps to a replay scrubber. Rolling back to tick N and *editing* (changing a parameter or rule, then re-simulating forward) is a feature edit followed by regeneration. Keeping the old recording and re-running it under the new rules is the deterministic analog of Fusion's dependency check. The per-tick hash diff (`first_divergence`) is the analog of features turning red: it shows the first tick where the new rules give a different outcome.
- *Undo stack versus editable history.* The editor's undo (scene diffs) is the linear edit log. The authored scene plus the input recording is the editable recipe. Keep them separate, as Onshape separates the feature list from microversions. Undo should operate on the recipe (as inverse diffs) and never mutate a replay's input log silently.
- *The topological naming problem has a direct analog.* A recorded input log, a scene diff or a saved game that refers to an entity *created during simulation* (a bullet, a spawned enemy) by Flecs id or creation index breaks when an earlier rule change alters what gets created. Mitigations, mapped from CAD: (1) reference authored entities by StableId (the "datum plane" advice); (2) give generated entities lineage-derived StableIds (spawner StableId plus spawn ordinal, like Onshape's tracking queries) so they re-resolve after an edit; (3) when a reference cannot be re-resolved after a rules edit, mark it broken and visible rather than rebinding it silently; (4) recorded *input* (keys and pointer per tick) is naturally robust because it refers to no entities. That is a reason to keep replays as input logs rather than as entity-level event logs.
- *Microversions equal content-addressed scene states.* Immutable, diff-based scene versions with a tree of branches fit the existing scene-diff history and would make "play from this version" (play in editor by snapshot) reproducible and shareable.
